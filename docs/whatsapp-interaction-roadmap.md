# WhatsApp 互動功能開發建議與可行性

面向 FINNE18／SK11：在 WhatsApp 完成公帳入數、提醒、報表等。本文說明**現況、可行性、限制與建議路線**。

相關實作：`docs/whatsapp-webhooks.md`、`src/lib/whatsapp/`、`/api/webhooks/whatsapp`。

## 1. 身份識別（已打通，請先填電話）

| 來源 | 說明 |
|------|------|
| **用戶資料 `contactPhone`** | 個人資料／管理後台填寫；儲存時正規化並**自動寫入 `WhatsAppBinding`** |
| **管理後台 → WhatsApp 分頁** | 手動綁定；會反寫 `contactPhone` |
| **環境變數 `WHATSAPP_USER_MAP`** | 緊急／測試用 |

## 2. 功能可行性總表

| 功能 | 可行性 | 建議型態 | 備註 |
|------|--------|----------|------|
| 查提醒（合約／事項／恆常） | ✅ 高 | 文字指令 `提醒` | **已有** |
| 公帳簡易入數 | ✅ 高 | `公帳 支 120 餐飲` → `確認` | **已有**；適合固定分類 |
| 最近紀錄／資金池／分類列表 | ✅ 高 | 文字指令 | **已有** |
| 本月收支文字摘要 | ✅ 高 | `報表`（管理員） | **已有**；非 PDF |
| 完整 PDF／會計結算包 | ⚠️ 中 | 產生後給**下載連結**或文件訊息 | ZIP／大檔不宜塞聊天；要短時簽名 URL |
| 多級分類＋附件入數 | ⚠️ 中 | 逐步對話或按鈕選單 | 文字易錯；照片需另接 media API |
| 發票／收據 OCR 上單 | ⚠️ 中 | 收圖 → OCR → 確認草稿 | 依賴現有 OCR；要下載 WhatsApp media |
| 事項／合約建立 | ✅ 中高 | 結構化指令或表單流程 | 欄位少，適合 |
| 審核通過／駁回 | ✅ 中高 | 管理員按鈕／指令 | 權限嚴格控管 |
| 薪金結算／發工資單 | ❌ 低（初期） | 僅推播「已出糧」+ 網頁連結 | 金額敏感，不建議 WhatsApp 改數 |
| 複雜報表篩選匯出 | ❌ 低 | 網頁為主 | 互動成本高於 H5 |

圖例：✅ 建議做｜⚠️ 可做但要設計｜❌ 不建議當主路徑

## 3. Meta／產品限制（設計時必顧）

1. **24 小時服務窗**  
   用戶傳訊後 24h 內可自由回覆；逾時只能用**已審核樣板訊息（Template）**（例如到期提醒）。

2. **Development vs 上線**  
   開發模式只能對測試號；正式用戶要 App／商務驗證完成。

3. **互動元件**  
   - 文字指令：最快上線（現狀）  
   - **Reply buttons / List messages**：選分類、確認入數（體驗更好）  
   - **Flows**：類似表單，適合多欄位「上單」

4. **媒體**  
   收圖／回 PDF 要用 Cloud API media endpoints；檔案要落自己的儲存再給連結較穩。

5. **安全**  
   電話≈身份，務必白名單／綁定；敏感操作要二次確認；審計備註保留 `[WhatsApp]` 前綴。

## 4.1 【已拍板】公帳分步＋OCR 工作流程（Meta 審核後執行）

### 產品目標

用戶在 WhatsApp 說要入公帳（或傳 `公帳`／直接丟收據圖）時，系統用**選單＋分步輸入**收集分類／金額／備註／附件，並可選**圖像辨識**後完成入帳——**不要**做成單一網頁式表單（WhatsApp 不支援同則訊息內嵌完整表單；先做分步對話）。

### 標準流程（實作時照此順序）

```text
觸發：用戶傳「公帳」／「上單」／「入帳」
      或直接傳收據圖片（image/document）

1) Bot：請選類型 → Reply buttons［支出］［收入］［取消］
2) Bot：請選分類 → List message（常用分類；「其他」可自打名稱）
3) Bot：請輸入金額（可回「OCR」交給辨識；可略過若已有圖）
4) Bot：備註？（可「略過」）／可再傳附件圖
5) 若有附件 → Bot：是否使用圖像辨識填補／核對？［是］［否］
6) 若「是」→ 下載 media → 呼叫現有 OCR → 合併草稿
   （手填優先；OCR 只補空白或提示差異）
7) Bot：確認卡（類型／分類／金額／備註／附件數／OCR 與否）
      ［確認］［改金額］［取消］
8) 確認 → createRecord（審核戶 → PENDING；備註加 [WhatsApp]）
```

### UX 原則（已確認）

| 原則 | 說明 |
|------|------|
| 先附件也可 | 直接傳圖應能開流程，不必先打「公帳」 |
| 手填優先、OCR 補缺 | 避免用戶手打金額又強制再 OCR 造成衝突 |
| 一定要確認卡 | 防誤入；確認前不寫 DB |
| 分類過多 | List 放常用；其餘走「其他」+ 文字 |
| OCR 失敗 | 保留手填，整單不作廢 |
| 多圖 | 皆當附件；OCR 可先跑第一張或摘要多張 |

### 技術實作清單（給後續 Agent）

- [ ] `WhatsAppSession`（或等效）表：`phoneE164`、`step`、`draftJson`、`expiresAt`（TTL ~30 分鐘）  
- [ ] 發送 Reply buttons / List messages（Cloud API interactive）  
- [ ] 入站處理 image／document：Graph media download → 存附件儲存  
- [ ] 串接現有 OCR action／lib，產出金額／備註建議  
- [ ] 草稿合併策略：user fields win；OCR fills nulls；差異列在確認卡  
- [ ] 重用網頁公帳建立邏輯與資金池審核規則  
- [ ] 指令 `取消`／逾時自動清 session  
- [ ] 保留現有一行指令 `公帳 支 120 餐飲 …` 作進階快捷（不刪）

### 前置條件（開發前勾選）

- [ ] Meta App 審核／WhatsApp 商務號碼可對正式用戶收發  
- [ ] Railway 已設 `WHATSAPP_ACCESS_TOKEN`、`WHATSAPP_PHONE_NUMBER_ID`、`WHATSAPP_APP_SECRET`  
- [ ] 操作者已綁定 `contactPhone`／WhatsAppBinding 且有公帳權限  
- [ ] Webhook `messages` 訂閱正常；測試號已能跑現有文字指令

### 觸發關鍵字（建議）

`公帳`、`上單`、`入帳`、`入數`，以及**純媒體訊息**（已綁定用戶、無進行中其他 session 時）。

## 6. 「生成報表」建議產品規格

| 等級 | WhatsApp 回覆 | 實作成本 |
|------|----------------|----------|
| L1 摘要 | 本月收入／支出／淨額／筆數 | 低（已有） |
| L2 明細精選 | 最近 N 筆或某分類合計 | 低 |
| L3 PDF | 產生後給 HTTPS 下載連結（5–15 分鐘有效） | 中 |
| L4 結算包 ZIP | 同上，僅管理員＋明確確認 | 中高 |

**不建議**把整份 PDF base64 塞進聊天；改用系統已有報表匯出邏輯 + 暫存檔／物件儲存 + 簽名 URL。

## 7. 技術注意（給後續 Agent）

- 指令與業務邏輯放 `src/lib/whatsapp/`，**不要**在 webhook route 堆業務。  
- 入數重用與網頁相同的資金池審核規則。  
- Pending 確認建議改獨立表（TTL），勿長期佔用 `SystemSetting`。  
- Template 訊息與服務窗回覆分開模組。  
- 所有 WhatsApp 寫入加來源標記，方便報表／稽核篩選。

## 8. 結論（給行銷／營運）

- **查提醒、簡易公帳入數、文字摘要報表**：現在就可作為 WhatsApp 主場景，可行性高。  
- **完整報表／結算包**：適合「觸發＋連結下載」，不適合全程在聊天完成。  
- **OCR 拍照上單、按鈕選單**：下階段 CP 最高的體驗升級。  
- **薪金改數、複雜篩選匯出**：維持網頁為主，WhatsApp 只做通知。

身份面：在**用戶管理／個人資料填好電話**即可；不必再維護兩套號碼。
